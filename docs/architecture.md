# Architecture

Triagent is a TypeScript monorepo run directly by Node 24 (type stripping, so the server has no build step).

```text
packages/shared   Vocabulary and the permission table, shared by server, web app and agents
apps/server       The API, MCP endpoint and webhooks (Hono); serves the built web app; queues reviews
apps/runner       Runs Open Code Review for the server: no database, no data volume, one job's credentials at a time
apps/web          The web app: React, TanStack Router and Query, shadcn/ui (built with Vite)
tests/contract    What any Triagent server must do, runnable against any implementation
tests/fakes       A fake GitHub (API, app auth, OAuth, git over HTTP) and a fake `ocr`, for tests
```

## Server layers

```text
http/route.ts      Route declarations: method, path, scope, permission, query and body schemas
http/mount.ts      One wrapper applies authentication, CSRF, workspace isolation, permissions and validation
routes/*.ts        Declared routes, grouped by area; handlers are a few lines each
mcp/*.ts           MCP tools, declared the same way (permission + zod schema) over the same services
services/*.ts      Behaviour: accounts, projects, reports, triage, settings, secrets, webhooks, events
domain/*.ts        Pure logic: parsing reports, a branch's read model, filters, Markdown
store/*.ts         The storage interface, with Postgres and in-memory implementations
db/migrate.ts      Applies the SQL migrations in apps/server/db/migrations
```

Requests flow `route → mount wrapper → handler → service → store`. Services never see HTTP; routes never touch storage directly for writes.

## Workspaces and permissions

Everything belongs to a workspace: a person's personal workspace, or an organisation. Paths carry it: `/api/v1/w/{workspace}/p/{project}/…`.

- A person's access comes from their **role** in that workspace (viewer, editor, admin, owner).
- An API token belongs to **one workspace**, has a **scope** (read, write, upload, full, manage), and **acts for a member** of that workspace. It never has more access than they do: its permissions are what its scope allows *and* their role allows now (`permissionsOf({ kind: "token", scope, role })`), checked on every request, every MCP call, each live stream's heartbeat (a role change also closes their tokens' streams) and when an upload link it made is used. It can't be made with a scope beyond its member's role, it loses what they lose, it's revoked when they leave, and a token acting for nobody isn't accepted. It never reaches the member's other workspaces.
- Both map onto one table of **permissions** (`packages/shared/src/permissions.ts`). Every route and MCP tool names the permission it needs; tests fail if one doesn't.
- `secrets`, `members`, `tokens` and `workspace` are **browser-only**: no token scope includes them, so a leaked token can't escalate and secrets never pass through an agent.
- Someone without access to a workspace gets 404 for everything in it, the same as for a workspace that doesn't exist. A test calls every route as an outsider to prove it.

## Writes

Every change runs in one store transaction (`Core.write`): it's applied completely or not at all, it's recorded in the activity log (triage and content) or the audit log (people, tokens, settings, secrets), and live updates go out only after it's saved. Issues and tasks carry a `rev`; a stale one is refused with 409 and the current version. Claims are conditional on the issue still being open and unassigned.

## Storage

Services talk to one interface (`store/types.ts`), implemented twice: `PostgresStore` when `DATABASE_URL` is set, and `MemoryStore` for development and tests. `NODE_ENV=production` refuses to start without a database. The same conformance tests (`apps/server/test/store.test.ts`) run against both, and CI runs every server test and the contract suite once with each.

- **Schema.** Plain SQL migrations in `apps/server/db/migrations`, applied in order at start-up and recorded in `schema_migrations`. Each runs in its own transaction under an advisory lock, so two servers starting together apply it once, and a migration that changed after it was applied stops the server. `node apps/server/src/db/migrate.ts` runs them alone. Everything a workspace owns has a `workspace_id`, or reaches one through `project_id`, with foreign keys that delete it along with its workspace or project. The audit log has no such key, so it outlives what it records. Reports, uploads, triage notes, settings and log changes are `jsonb`.
- **Transactions.** Services read a record, decide, and write it back, relying on nothing changing in between (revision checks, claims, "re-read before saving"). The memory store gets that by running transactions one at a time. Postgres runs them concurrently at `SERIALIZABLE` isolation: a transaction that overlapped another in a way no one-at-a-time order would allow is refused (serialization failure or deadlock, or a unique key two transactions both checked was free) and run again from the start, a few times at most, after a short random wait. Callbacks must therefore be safe to re-run: anything that should happen once a change is saved, such as live updates, is registered with `store.afterCommit` and runs only after the outermost transaction commits. The current transaction travels in `AsyncLocalStorage`, so a transaction started inside another joins it, and a store call made inside a transaction uses it even when it isn't made through `tx`. A write outside any transaction is a transaction of its own.
- **Ordering.** Report versions come from a sequence, so they only go up. Activity and audit rows are listed newest first by an internal sequence number; callers page with the `id` of the last row they saw.
- **More than one process.** With Postgres, live updates (and "close these streams" when someone loses access) also go out through `LISTEN/NOTIFY`, so they reach subscribers on every server process sharing the database.
- **Not yet.** Row-level security, as a backstop to the workspace checks in the services, comes with multi-workspace hardening (Phase 7).

## Signing in

`AUTH_MODE=local` keeps usernames and scrypt-hashed passwords; `AUTH_MODE=oidc` signs people in through an OpenID Connect provider (`services/oidc.ts`, with `openid-client`), matching accounts by the provider's issuer and subject, never by email. With a provider, accounts are created on first sign-in only for invited (verified) addresses, the admin group, or the first account, and instance administrators follow the provider's admin group (`services/invites.ts`, `services/accounts.ts`). Sessions record when the person last authenticated: changes needing `secrets`, `members`, `tokens` or `workspace` (and the instance's accounts, invites, keys and grants) also need that to be recent (`REAUTH_MINUTES`), checked once in `http/mount.ts`, and otherwise answer 401 `reauth_required`. A provider that doesn't say when the person authenticated (`auth_time`) doesn't count as a recent sign-in. Details, settings and an Authentik walkthrough are in [authentication.md](authentication.md).

## Secrets

GitHub credentials, webhook secrets and model keys are encrypted with AES-256-GCM under a key that's never stored with the data (`TRIAGENT_SECRETS_KEY_FILE`). Each is bound to its workspace, project and name as authenticated data, so a ciphertext moved elsewhere fails to decrypt. The API only says whether a secret is set, its last four characters, and who set it when.

## Insights: analytics, prices and allowances

- **Review history.** Every finished review is one row in `review_history`: a run on the server (recorded by the run itself, with its queue and run times), or an uploaded report (recorded by `services/reports.ts` in the upload's own transaction, from what the report says about its run: model, tokens, elapsed time, tool calls, retries, file groups it couldn't finish). Uploads by GitHub automation are server runs and aren't recorded twice. Each row also keeps the ids of the findings that review reported first (by severity), so analytics know when a finding first appeared. Neither the history nor the activity log has a foreign key to projects: deleting a project keeps both, so analytics still count its past reviews and triage, unless the delete asks for them to go too (`DELETE /api/v1/w/{workspace}/p/{project}` with `purgeAnalytics: true`, a checkbox in the delete dialog). A tutorial example's always go with it.
- **Analytics** (`GET /api/v1/w/{workspace}/analytics?project=&branch=&days=`, MCP `get_analytics`; `project` is a project's slug, as in its address, or empty for all of them) reads three things, each with a bound: the history (all branches, so first sightings are known; at most 20,000 rows), the activity log back to the start of the range (at most 50,000 rows), and the current reports of the branches in scope (at most 200,000 findings; past that the remaining branches aren't read). An answer that hit a bound says which (`truncated`), and the page says so. `domain/analytics.ts` works through each list once. Ranges up to a month are counted by day (UTC), longer ones by week (starting Monday). Medians and 90th percentiles interpolate. A figure no review recorded is "not recorded", never zero. Time to resolve runs from a finding's first sighting in the history; findings first seen before the history began aren't timed.
- **Model prices** are US$ per million tokens (input, output and, optionally, cache reads). A workspace's own price (`configure`) wins over the instance's (instance admins), which wins over OpenRouter's listed price. Costs are worked out when analytics are read, so new prices apply to past reviews. Input tokens are taken to include cache reads, which are charged at the cache-read price (or the input price without one). Models without any price are listed, and their tokens left out of costs.
- **OpenRouter's catalogue** (model ids and prices, for the model picker and default prices) is fetched by the server, never the browser: an 8-second timeout, kept an hour, a failed fetch keeps the older copy and isn't retried for five minutes. `OPENROUTER_CATALOGUE=false` turns it off.
- **The instance model key.** An instance admin stores a key per provider (encrypted, `workspace_id` null) and chooses the instance's provider and model, then grants chosen workspaces a monthly token allowance (`model_grants`). `Models.forRun(workspace)` decides what a review runs with: the workspace's own key for its chosen provider; otherwise, with a grant, the instance key while this calendar month's (UTC) instance-key tokens are under the allowance; otherwise not ready, with the reason (for example, when the allowance resets). The check is made when a review starts, and each instance-key review is given a token budget (`--max-tokens-budget`) out of what's left: the allowance, less this month's tokens, less the budgets of the workspace's instance-key reviews running now (set aside until they finish, so reviews running at once can't each be handed the whole remainder; the claim runs in one transaction). With less than 10,000 tokens left (the smallest budget a review can run with) the allowance counts as used up, and the Runs page says why. Every instance-key review counts, however it ends: the larger of its report's tokens and what OCR said while it ran (the runner reads OCR's usage record and budget messages from its stderr), or, when there's no figure at all (a time limit, a stall, a cancel, a lost runner), the whole budget it was given, marked `estimatedTokens` and shown in analytics as an estimate. A review that never reached OCR (the fetch failed, say) is reported by the runner as using none. Grants, keys and prices are audited; keys are never returned.

## Model providers

The providers reviews can use are one registry (`services/providers.ts`): for each, the protocols Open Code Review (OCR) speaks to it, its base URL, where to get a key, whether it lists its models, and a few suggested models (suggestions only: any model id can be typed in). `services/model-setup.ts` keeps a workspace's configuration (and the instance's, for the instance key) the same way: its favourite models and which is the default (below), each provider's own settings (`protocol`; an endpoint URL for Azure and custom servers; an AWS region for Bedrock) in the settings tables, and its secrets (`model-key:{provider}`, and Bedrock's `model-key:bedrock:access-key-id`) encrypted, write-only, needing a recent sign-in to set. `Models.forRun` resolves it to what OCR needs, and the claim hands the runner exactly that for the one job.

**Favourites.** A workspace's `review-model` setting also holds `favourites: { id, provider, model, name? }[]` and `defaultId`: the models it uses, across however many providers it has connected (Settings → Models), each a provider's model with an optional nickname, one the default. Ids are short, random and never change, so other settings can refer to a favourite and a rename breaks nothing. The rules (`services/model-setup.ts`): the provider exists, the model name is valid, at most 20, no provider's model twice, nicknames up to 40 characters; the first favourite is the default; the last one can't be removed, and the default only by naming the favourite that takes over. A favourite is ready when its provider has everything it needs (key, endpoint, region), and otherwise says what's missing; `resolveFavourite(repos, workspace, id)` gives what one would run with. Routes are under `…/settings/models/` (`favourites` to list, add, change and remove, `favourites/order`, `default`), reading with `read` and changing with `configure`, so a token with the `manage` scope can manage favourites but never keys. `PATCH …/settings/review-model/providers/{id}` changes one provider's settings without choosing it, behind the same guard on a keyed provider's address.

**Which models a review uses** (`services/models.ts`, `forProject(workspace, project, kind, requested)`). The first of these that says:

1. the run's own choice: `models` on `POST …/reviews` or the MCP `start_review` tool, kept on the job as `requestedModels`;
2. the project's set for that kind of review (`pr`, `changes`, `full`);
3. the project's set for every review (`all`);
4. the workspace's default (`forRun`): the default favourite, or the instance's model within an allowance when that isn't ready.

Each of 1 to 3 is one to five ids (`MAX_MODELS`) of the workspace's favourites, or `instance`: the instance's model, which can be chosen like a favourite, alone or with others, while the workspace has an allowance. It keeps `keySource: "instance"`, and the allowance (used up, set aside by running reviews, what's left) is checked for that model only. Automatic reviews (pull requests, the nightly scan) have no choice of their own, so they start at 2. A project's sets are its automation setting `models: { all?, pr?, changes?, full? }`; a set left out or empty falls through. Saving checks that every id is one of the workspace's favourites (or `instance`, with an allowance), each once in a set. Starting a review checks its `models` the same way.

A model that isn't ready keeps the review queued, with a reason naming it. A favourite the run asked for that has since been removed can never become ready, so that review fails, saying so. Labels are a favourite's nickname or its model name, with the provider added when two in one review share that. The job records each model's id, provider, model, label, whose key paid and its budget when it starts, so renaming or removing a favourite later doesn't change what a run says it ran with.

`GET /api/v1/w/{workspace}/models` (`read`; the MCP `list_models` tool) lists the favourites with their readiness, the default, the instance's model when there's an allowance, and with `?project=` what each kind of review of that project uses and which rule says so. The web's pickers read it.

Before favourites a project listed its models as `{ provider, model }[]`. Such a list is converted the first time the setting is read (`Settings.automation`): each entry becomes the favourite that is that model, added to the workspace's favourites if it isn't one, and the list becomes the project's `all` set. The favourites and the setting are saved together in one transaction (joining the reader's, if it has one), so the ids are fixed from then on and two readers at once end up with the same thing. An empty list just reads as no choice and is rewritten the next time the settings are saved. There is no SQL migration; the models a run was asked to use are kept in the job's `requested_by` JSON for the same reason.

Removing a favourite that projects' sets use, or that a project's reviews ask which findings are the same problem (`options.judge`), is refused with 409, `code: "favourite_in_use"` and the `projects` (each with the `sets` it's in, and `judge: true` when it's the one asked), unless `?force=true`, which takes it out of those sets in the same transaction (a set left empty falls through) and leaves such a project asking nobody. Renaming a favourite changes nothing for the projects that use it: they name it by id. A queued run that asked for it fails when its turn comes, as above.

The older fields are kept and always say what the default favourite is: `provider` is its provider and `models[provider]` its model. So `forRun`, the allowance view, the setup checks and `GET …/settings/review-model` (which now also returns `favourites` and `defaultId`) read what they always did, and `PATCH …/settings/review-model` still chooses the default: the favourite that is that model already, otherwise the default favourite changed in place (same id). There is no SQL migration. Settings saved before favourites are read as one favourite, their provider and its model, with an id derived from the two so it's the same on every read, and are written in the new shape on the next save. A workspace that has never chosen anything has no favourite until its usual provider (OpenRouter) is set up, so one that starts with another provider has no stray entry. The instance model has the same shape and stays a single favourite.

**How the runner drives OCR** (checked against OCR 1.12.12's `internal/llm/resolver.go`, `client.go` and `protocol.go`, and by running the binary against a local fake provider; `apps/runner/test/ocr-protocols.test.ts` does that too with `OCR_REAL_BIN` set). OCR tries its config file first, then `OCR_LLM_*`. The job's HOME is empty, so for every protocol but Bedrock there's no config file and OCR reads `OCR_LLM_URL`, `OCR_LLM_TOKEN`, `OCR_LLM_MODEL` and `OCR_LLM_PROTOCOL`. `OCR_LLM_PROTOCOL` wins over `OCR_USE_ANTHROPIC` (which, unset, would mean the Anthropic protocol); the runner sets it to agree anyway. Per protocol:

- `openai`: `POST {url}/chat/completions`, `Authorization: Bearer`. Azure's v1 API takes its key this way too.
- `openai-responses`: `POST {url}/responses`, `Authorization: Bearer`.
- `anthropic`: `POST {url}/v1/messages`. From the environment OCR sends the key as a bearer token unless `OCR_LLM_AUTH_HEADER=x-api-key`, which the runner sets (Anthropic's own header; OCR's preset uses it too).
- `anthropic-bedrock`: OCR refuses it in `OCR_LLM_PROTOCOL`, so the runner writes `~/.opencodereview/config.json` in the job's throwaway HOME (mode 0600) with only `{"provider": "bedrock", "providers": {"bedrock": {"aws_region", "model"}}}`: no keys, MCP servers, setup or `api_key_cmd`. The credentials are `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` in OCR's environment, with `AWS_REGION` and `AWS_EC2_METADATA_DISABLED=true`, so the AWS SDK never falls back to the runner host's own role. OCR signs with SigV4 and the region decides the host.

**Model lists** (`GET …/settings/review-model/providers/{id}/models`, `read`; `GET /api/v1/instance/model/providers/{id}/models` for the instance key) are fetched by the server with the stored key: `{url}/models` with a bearer key, Anthropic's `{url}/v1/models` with `x-api-key`, Cohere's own `https://api.cohere.com/v1/models` (its compatibility API has none), OpenRouter's catalogue. Kept ten minutes (a failure, one), 8-second timeout, 4 MB at most, redirects refused. Only ids and names go back; never the key, nor what the provider said (an error body could quote the key). Bedrock, Azure (its list names models, not deployments), Fireworks and Qwen have no list here: suggestions and free text.

**Custom and Azure URLs** must use https and resolve only to public addresses: every address the name resolves to is checked (private, loopback, link-local and cloud metadata, carrier-grade NAT, multicast and reserved ranges, IPv6 unique-local and link-local, and IPv4 inside IPv6), and user names, passwords, query strings and fragments are refused (`services/model-urls.ts`). They're checked when saved, before each model-list fetch, and again when a review is claimed (a URL that now resolves privately fails the review, saying why). `ALLOW_PRIVATE_MODEL_URLS=true` lets an instance use private addresses (a self-hosted Ollama), and plain http to them only. Not covered: DNS rebinding, a name that resolves to a public address when checked and to a private one when OCR or the server connects. The check narrows what a URL can reach; the runner's network (outbound only, no route to the database) is the boundary.

**Prices.** Analytics price a model by its own name, or failing that by the OpenRouter catalogue id the same model has, where that's clear: `claude-sonnet-4-5-20250929` and `us.anthropic.claude-sonnet-4-5-20250929-v1:0` are `anthropic/claude-sonnet-4.5`, `gpt-…` is `openai/gpt-…`, `gemini-…` is `google/gemini-…` (and likewise for xAI, DeepSeek, Mistral, Cohere, Kimi and Qwen), but only if OpenRouter lists exactly that id. Anything else (an Azure deployment, a custom server's model) has no price unless one is set.

## Reviews: the queue and the runner

A review is a job in the store (`jobs`, migration 0003): queued, then claimed by a runner, then finished. `services/runs.ts` owns it.

```text
person / token / automation ──▶ POST …/reviews ──▶ jobs (queued)
                                                     │  claim (fair, capped, model ready)
runner ◀── /internal/runner/claim ──────────────────┘   job + this job's GitHub token and model key
runner ──▶ …/heartbeat, …/events (log, progress) ──▶ lease renewed, log and progress redacted and stored (≤ 2 MB)
runner ──▶ …/finish (report) ──▶ one transaction: upload to the branch, review history, activity
                                 then (after commit): the pull request's comment and commit status
```

- **Queueing.** Each job records the repository it was queued for (GitHub's id when known, and owner/name). If its project is pointed at another repository before it starts, it fails, saying so, rather than reviewing the other repository's code; if that happens while it runs, nothing is posted to GitHub, and its log says why. Each job has a key for what it reviews (`pr:12`, `changes:feature:main`, `full:main`). A newer request with the same key replaces a queued one; a request for a commit already queued or running returns that job. Starting a review checks GitHub first (the pull request is open, the branches exist, there's something to review).
- **Scheduling** happens when a runner asks for work, in one transaction, within three limits: how many reviews run at once on the instance, how many in the job's workspace, and how many the asking runner works on at once (below). Workspaces take turns: the one whose last review started longest ago goes first, oldest job first within it. A job only starts when its models are ready (`models.forProject`: see Which models a review uses); until then it waits, and the Runs page says why. The models (and whose key pays for each) are recorded on the job when it starts, with its `--max-tokens-budget`: the project's, and for the instance's model that capped by what's left of the allowance.
- **Limits** (`services/review-limits.ts`). An instance admin sets the first two in Settings → Instance → Reviews (`GET` and `PUT /api/v1/instance/reviews`: `{ instance, perWorkspace }`, each 1 to 100), and can give a workspace a limit of its own on the Workspaces page (`PUT` and `DELETE /api/v1/instance/workspaces/{workspaceId}/review-limit`), lower or higher than the others'. A workspace never runs more than the instance's limit, whatever its own says. They're one instance setting (`review-limits` in `instance_settings`: no migration), read inside the claim's transaction, so a change needs no restart and applies to the next review to start on every server process. Nothing running is ever stopped: after a limit is lowered below what's running, no more start until enough have finished. `REVIEW_CONCURRENCY` and `REVIEW_CONCURRENCY_PER_WORKSPACE` (default 1 each) are what apply on an instance that has never saved the two numbers; after that they're ignored. Changes are audited (`instance:review-limits`; `workspace:{slug}:review-limit`, and `review-limit` in the workspace's own log). `GET …/runs` gives `concurrency: { instance, workspace }`, where `workspace` is that workspace's own limit as it applies (never another's), and a queued review says which limit it waits on.
- **Runner slots.** A runner says with every request how many jobs it works on at once (`capacity`, its `RUNNER_CONCURRENCY`) and how many more it can take now (`slots`). The claim hands out one job at a time, none to a runner with no room, and none to a runner already holding as many as it works on at once, counted from the jobs the server has it down for. The limits can be set above what the connected runners can do: reviews then wait for a free runner slot, and say so. The Reviews page lists the connected runners (name, version, slots in use of slots, last seen). A runner older than `capacity` only sends `slots`: the server believes it, as before, and takes its slots to be that many and the jobs it holds. A server older than `capacity` ignores it. Two claims racing for the last place (on the instance, in a workspace, or of one runner) can't both win: in memory transactions run one at a time, and Postgres refuses one of two overlapping claims and runs it again, when it sees the place has gone (`test/review-limits.test.ts` races them against both).
- **Leases.** A claimed job has a 60-second lease, renewed by the runner's heartbeats (every 10 seconds) and log batches. A job whose lease runs out is failed, saying the runner stopped responding; the server checks every 15 seconds and at start-up, so jobs left running by a crashed or restarted runner don't hang. A runner that lost its job gets 409 and stops. Cancelling a queued job ends it at once; cancelling a running one is passed to the runner with its next heartbeat or log batch, and it stops whatever is running: `git fetch` or `git worktree add`, or OCR's whole process group. A runner that loses its job stops the same way.
- **What runners send** is redacted (see the threat model) and stripped of characters Postgres text can't hold (NUL), so one odd line can't stop a job's log being stored. A runner whose batch is refused (a 4xx other than 409) drops it rather than sending it again forever; it keeps lines only while the server can't be reached. A report that isn't shaped like OCR's (findings that aren't objects, say) ends the job as failed, saying why; recording how a job ended never leaves it running.
- **Finishing.** The report is uploaded to the job's branch with `services.reports.upload` as a `via: "github"` actor (so the upload isn't counted again as an uploaded review), with `confirm: true` and scope `diff` for pull requests and branch changes. The run records its own review history (`services/history.ts`, using `domain/review-metrics.ts` for tokens, tool calls and file groups, and the ids of findings it reported first). A run whose report says some file groups didn't finish is `partial`, with the files named. Failed and cancelled runs that started are recorded too, with the tokens they used (see the instance model key above for runs that never said).
- **Several models.** A review can use up to five models (a project's sets, or the run's own choice); each uses the workspace's key for its provider, or for the instance's model the instance's key and the workspace's allowance. The job gives the runner a token budget for the job and, for the instance's model, one of its own (`models[].maxTokensBudget`); the job's is the tighter of the two, so a runner that only knows that one can't overspend an allowance. An instance-key model that ends without saying what it used is charged its whole budget, as a single-model run is, unless the runner reported and it never had its turn. The runner reviews with all of them at once (at most `RUNNER_MODEL_PARALLELISM` at a time; the rest wait their turn inside the job): a process each, on the same worktree, with a fresh `HOME`, environment, time limit and stall check of its own. Its log lines start with the model's label (`[label] …`), its progress is its own (`progress.models[i]`: `label`, `phase` (`waiting`, then OCR's, then `done`, `failed` or `cancelled`), files, round, tokens, `startedAt`, `seconds`, `reason`), and the job's own progress fields are all of them together (tokens and tool calls added up, the phase of whichever running model is furthest behind). One model failing or stalling leaves the others alone; cancelling stops them all. A model whose reported tokens pass its token budget is stopped by the server: the reply to `…/events` and `…/heartbeat` is `{ cancel, stop: [{ index, label, reason: "overBudget", budget }] }`, where `stop` names models by their place in the job (a runner that only knows `cancel` ignores it, and a server that doesn't send it stops nothing). OCR ends a review that reaches its budget by itself and keeps what it found, so the stop is a backstop: the runner logs the order and gives that model `RUNNER_OVER_BUDGET_GRACE_SECONDS` (default 120; 0 for none) to finish. One that does is reported as it would be anyway (done, with its findings); one still going after that is stopped alone and reported as failed with `reason: "overBudget"`. Cancelling during the wait stops it at once. It sends each one's outcome (`parts`, with `reason` `stalled`, `timeLimit` or `overBudget` for one that was stopped), and the run keeps them in `result.models[].reason` (null otherwise). The server merges the reports (`domain/merge.ts`): findings from different models at the same place (same file and category, lines within three of each other) are one finding, marked `found_by` every model that found it, the first model's wording leading and the others' kept as `also`; one model's own findings are never merged with each other. A model that failed makes the review `partial`, naming the model (but not why: the note is posted on GitHub). The review history gets a record per model (its own findings, tokens and time), grouped by `details.scan`, so analytics count the scan as one review and compare the models side by side. Triage filters with `foundBy` (at least that many models) and sorts by `agreement`.
- **Options for several models.** A review with two or more models can be given options (`packages/shared/src/run-options.ts`): `options` on `POST …/reviews` and the MCP `start_review` tool, the Options on Start a review, or the project's own (`automation.options`, Project settings → Review models) for reviews that don't say, automatic ones included. Each is off unless chosen; `options: {}` means none, whatever the project's are. They're kept with the job (inside `requested_by`, like the models it was asked to use): those asked for while it's queued, and from the claim on those it runs with, worked out once its models are known (`effectiveOptions`). A review with one model has none: asking for them outright is refused with a 400, and a project's own are left off with a line in the run's log.
    - **Agreement rules** (`options.agreement`) change the pull request's check and how findings are listed, and nothing else: every finding is kept and triage is as it was. `failAt: N` fails the check only for critical findings at least N of the review's models found (by the finding's own rating, the lead model's); when fewer than N models finished, all that did must have found it, so a rule nothing can meet never passes a review by itself. The count is kept as `result.agreement` (`{ models, critical }`) and read by `finishedStatus` and the comment, which says when the check passes because of the rule. It only matters while the project's `failOnCritical` is on. `markSingles: true` is written into the merged report (`mark_singles`), so wherever findings are listed (the web app, `GET …/issues`, the MCP `list_issues` and `claim_next_issue` tools) one that a single model found has `lowerConfidence: true`, comes after the others of its severity in the default order, and can be filtered with `lowerConfidence=true|false`. The list says whether the report marks them (`markSingles`).
    - **Running a model again.** A model that failed, went quiet or was stopped in a finished review that made a report can be run again by itself: `POST …/runs/{runId}/models/{index}/rerun` (the same permission as starting a review), the MCP `rerun_model` tool, or Run it again on the review's page. That queues an ordinary job with one model (`rerunOf` names the review, the model's place, the attempt, and the id of the report the review made), which the claim tells to review exactly the review's commits (`commit: { head, base }`; the runner fetches what the job reviews as usual, then checks those commits out, asking GitHub for one that's no longer in the history). When it finishes, `reports.addModelFindings` adds its findings to that report (`domain/merge.ts`, `addModel`): a finding at the same place as one already there joins it (`found_by`, `also`), the rest are added after, and nothing already there moves or changes its wording, so ids, and with them triage, are exactly as they were; nothing is reopened. Only into the report the review made, compared by the upload's id: if the branch has another by then, asking is refused (409), and a job that finds so when it ends changes nothing and says why (`result.rerun.notAdded`), as does one from a runner too old to know `commit` that reviewed another commit. While it's queued or running it leaves the pull request's check alone and automatic reviews don't count it (`onTheSide`); once its findings are in, the check and comment are posted again from the whole report. The review points at its attempts (`result.retries`), and `GET …/runs/{runId}` lists them as they stand (`retries`) with the models that can be run again or why not (`rerunnable`). Its history record carries the review's `details.scan` and `details.attempt`, so analytics count it under the same scan. `options.retryFailed` does the same without being asked when the review ends, once for each model that failed (not one stopped for passing its token budget, which would only pass it again); a model run again is never itself retried, so it can't loop.
    - **A model asked which findings are the same problem** (`options.judge`: a favourite's id, or `"first"`/`true` for the review's first model that can be asked). The merge by place leaves apart findings two models put in different categories or more than a few lines from each other. With this option, the pairs worth asking about are worked out by a pure function both sides share (`packages/shared/src/merge.ts`, `candidatePairs`: two groups in the same file that no model is in both of, each stood for by its leading finding, the closest in lines first, at most `MAX_JUDGE_PAIRS` = 200 a review), and **the runner asks, not the server**: the server never calls a model. The claim gives the runner the model with this job's credentials for it (`judge`, a `RunnerModel` like the review models', its key redacted from everything the same way; its URL is checked again like theirs). After the reviews, the runner (`apps/runner/src/judge.ts`) puts the pairs to it 25 at a time over plain HTTP in the model's protocol (`openai`: `{url}/chat/completions`; `openai-responses`: `{url}/responses`; `anthropic`: `{url}/v1/messages`), with a time limit (`OCR_LLM_TIMEOUT`, else two minutes a request), no redirects followed, and at most 1 MB of answer read. OCR has no way to ask a question of one's own, which is why this is the runner's own small client; Amazon Bedrock needs AWS-signed requests, so a model there can't be asked (refused when chosen, and left out of the list to choose from), and nor can the instance's model (its tokens are an allowance's). The model is sent each finding's text (cut to 1,200 characters), severity, category, file and lines, and **never the code**: not the checkout, and not the `existing_code` or `suggestion_code` a finding quotes. That text came from a model reading untrusted code, so it's sent as data with an instruction to follow nothing in it, the answer must be one JSON object of pair ids to `true` or `false`, and anything else (a missing pair, `"true"` as a string, prose only) is no answer at all. All the pairs answered, or none. The runner sends what it got with the finish request (`judged: { pairs: [{ a: { part, index }, b: { part, index }, same }], total, tokens: { input, output }, seconds, error? }`); the finish route takes it as it comes and `readJudged` checks it strictly against the reports themselves (at most 200 pairs; both findings exist; different models; the same file; one of the pairs the server itself would have asked about; none twice), and one bad pair means none are used. Confirmed pairs are joined in the merge like any other agreement (`found_by`, `also`), unless that would put two of one model's findings in one. If the model fails, times out or answers nonsense, if the answers are refused, or if the runner is too old to ask, the review keeps the merge by place and says why (`result.judge.error`, and the log). `result.judge` has the model, `candidates`, `asked`, `same`, `merged` and its `tokens`, which are added to the run's; the history gets a record for it marked `details.merging` under the review's scan, which analytics show as `merging (model)` beside the models, never as a review of its own. A model run again by itself isn't compared this way: its findings join by place.
    - **Comparing models only** (`options.bakeOff`, never a project's own: Start a review → Compare models only). The models review as usual, but nothing goes to the branch: no report is uploaded, so the branch's report, its triage and its history are exactly as they were, and no upload is recorded for the backlog figures. Nothing is posted on GitHub either, at any point: no pending, passing or failing commit status and no comment (a comparison says nothing about whether the pull request is good, and a failing check from one would block a merge for no reason). It has a key of its own (`compare:pr:12`), so it neither replaces nor waits for a review of the same thing, and automatic reviews don't count it (`onTheSide`): it isn't "the review" of a pull request, nor the scan that makes a nightly one unnecessary. It takes none of the options about the report or the check (`retryFailed`, `agreement`: a 400 says so); `judge` works as in a review. If its models are down to one by the time it starts, it fails saying so rather than running as an ordinary review. What it found is kept with the run (`result.bakeOff`, `domain/bake-off.ts`): each model's findings (how many only it found, how many another found too, by severity), tokens and time, the overlap between each pair, and the merged findings with who found each (at most 500, the most agreed on first; `truncated` says when there were more). Lists of runs carry the figures without the findings; `GET …/runs/{runId}/comparison` (and the MCP `get_comparison` tool) returns it all, with each model's cost from the workspace's prices, and the web app shows it on a page of its own (`/comparisons/{runId}`). Its history records are marked `details.bakeOff` under one scan, so analytics count it for the models (tokens, cost, time, findings) like any review; the Models tab that will set comparisons side by side comes later. A model of a comparison can't be run again by itself: there's no report for its findings to join.
- **Live updates.** Runs announce `run` notices (queued, started, progress at most once a second, finished) to the workspace. The web app refetches only run queries on progress, and fetches a run's log from the last line it has.

### The runner (`apps/runner`)

A separate Node process with no database driver and no data volume. It talks to the server's `/internal/runner/*` API with a shared secret (`TRIAGENT_RUNNER_SECRET`, or `_FILE`, on both sides), which is the only credential those routes accept: it's compared in constant time before the body is read, and sessions and API tokens are refused. **The reverse proxy must not expose `/internal/`**; runners reach the server on a private network of their own. Branch names the runner is given are checked with git's own rules (as `git check-ref-format --branch`, so `fix#12` is fine) before they reach a git command.

For each job the runner:

1. fetches into a bare mirror per repository (`RUNNER_CACHE_DIR`, kept between jobs; nothing else is), one fetch at a time into each mirror (below), with the token in an `http.<origin>/.extraHeader` set through `GIT_CONFIG_*` variables: never on a command line or in a stored remote URL. Hooks are off (`core.hooksPath=/dev/null`), submodules aren't fetched, LFS doesn't run, redirects aren't followed and only the clone URL's protocol is allowed;
2. adds a detached worktree of the commit, its own (below). For a pull request or branch changes, everything that decides what OCR looks at comes from the base commit, not the change: `.opencodereview/` (or none, if the base has none), every `.gitignore` the change adds or edits (root or nested; OCR leaves out files the root one matches), the rule files the base's `rule.json` names (`"rule": "docs/review.md"`), and `.gitattributes` (checked out, and read by every git command OCR runs, with `GIT_ATTR_SOURCE`, so `-diff` or `binary` can't turn changes into "Binary files differ", which OCR skips). That needs git 2.42 or later: the runner checks `git --version` at start-up and won't start with an older one;
3. runs `ocr review --from <merge base> --to <head>` (or `ocr scan`), once per model for a review with several, with an environment built from an allowlist: a throwaway, empty `HOME` (OCR reads its user config and global rules from `~/.opencodereview/`, so there are none; it doesn't read `OCR_CONFIG_PATH`), `OCR_NO_UPDATE=1`, the model's settings for its protocol (see Model providers: a URL, key, model and protocol, or for Bedrock AWS credentials and a config file naming only the provider, region and model), and git settings that keep hooks off. Nothing else from the runner's environment, so never telemetry settings (`OCR_ENABLE_TELEMETRY`, `OTEL_*`) or `ANTHROPIC_*`;
4. streams OCR's stderr as log lines and progress (phase, files, file groups, round, tool calls), and stops it (the whole process group) on cancel, at the project's time limit if it has one (`reviewTimeoutMinutes`, `fullScanTimeoutMinutes`; none by default), or as stalled when it has printed nothing for the project's `stallMinutes` (30 by default; null switches the check off). The limits are per model's review, and a stalled review says so, apart from one that ran out of time;
5. deletes the worktree and the job's home directory, and reports the outcome (retrying for a while if the server is briefly away).

**Several reviews at once.** Jobs for different repositories never wait on each other. Two for the same repository share its mirror, so:

- **One fetch at a time into a mirror** (`apps/runner/src/lock.ts`): a queue inside the runner, and for runners sharing a cache volume a lock on disk beside the mirror (`<mirror>.lock`). The lock is a directory holding one file named by its holder. It's taken by renaming a directory made ready beforehand, with the file in it, into place, which the file system only allows onto nothing or onto an empty directory: so there is never a moment when the lock exists without its holder, and two runners can't both take it. The holder rewrites its file every few seconds. A waiter that sees a file unchanged for 30 seconds *of its own time* takes its holder for dead and removes that file, by name, which can only ever release that holder: two waiters breaking the same lock, or one slow to act, never touch the lock of whoever took it next. No clocks are compared (containers sharing a volume may disagree) and no process id is read (it means nothing in another container, and gets used again). A review that's cancelled, or loses its job, stops waiting at once and leaves nothing behind; while it waits its log says "Waiting for another review's fetch of this repository…". A cache directory that can't be written to fails the review at once, saying so, rather than waiting. A holder that was only stalled for longer than 30 seconds (not dead) loses the lock without knowing until its next refresh; two fetches then overlap, which git survives (it locks each ref it writes), though one may fail and say so.
- **A worktree per job**, at `<work dir>/job-…/tree`, recorded in the mirror under a name git makes unique. Adding one while another job fetches, or adds its own, is safe (git's own locking; checked by running them against each other), so only fetches take turns and a long checkout holds nobody up. Each is locked in the mirror (`git worktree add --lock`), and a job removes its own record and nothing else: nothing runs `git worktree prune` over the mirror any more, because to a runner in another container a running review's worktree directory doesn't exist, and pruning would take its record away mid-review. A runner that dies leaves its records behind; a running review marks its own as in use every ten minutes, and records not marked for a day are removed at the next fetch. So that nothing stays in a mirror for ever, records no runner marks (not locked at all, as an earlier version's were; left half added by a git that was killed; or too broken to say what they're for) go once nothing in them has changed for eight days, longer than any review may run. A worktree someone locked for a reason of their own is left alone.

`RUNNER_CONCURRENCY` (default 1) is how many jobs one runner works on at once. `RUNNER_OVER_BUDGET_GRACE_SECONDS` (default 120, 0 to 3600) is how long a model the server says has passed its token budget gets to finish by itself before the runner stops it. `RUNNER_MODEL_PARALLELISM` (default 5) is how many of one job's models review at once, so one runner can have up to `RUNNER_CONCURRENCY` × `RUNNER_MODEL_PARALLELISM` OCR processes going at once: give it memory for that, or lower either.

### Reviewing untrusted code: the threat model

A pull request's code is untrusted, and an LLM agent reads it. What it could try, and what stops it:

- **Run commands.** OCR's agent has only read-only tools confined to the repository (`file_read`, `file_read_diff`, `file_find`, `code_search` via git grep with traversal checks, `code_comment`, `task_done`): no shell. MCP servers and setup commands come only from OCR's user config (`~/.opencodereview/config.json`), which the runner never provides with either: each review gets a new, empty `HOME`, where only a Bedrock review gets a config file, naming its provider, region and model and nothing else. Git hooks, filters, `fsmonitor` and submodules are off in every git command the runner or OCR runs.
- **Hide its own changes.** OCR reads `<repo>/.opencodereview/rule.json` to decide what to include, exclude and focus on (and the files of instructions its rules name), leaves out files the root `.gitignore` matches, and skips files git calls binary, which `.gitattributes` decides. A pull request could add or change any of these to keep what it changes out of the review, so changes under review always get the base commit's: the runner puts them back as the base has them (removing what the base doesn't have, and never writing through a link the change added), and OCR's git reads attributes from the base. The change's own versions of these files are still in the diff, so they're reviewed like anything else. Full scans use the branch's own (they're requested by someone with `operate`, usually of the default branch).
- **Steal credentials.** The runner holds only the job's GitHub token (an installation token minted for that job alone, narrowed to the one repository with `contents: read` and revoked when the job ends, or the project's fine-grained token) and the model's credentials (a key; for Bedrock an AWS access key ID and secret access key), in memory, for that job. OCR never sees the GitHub token. The runner and the server share one redaction function (`packages/shared/src/redact.ts`), and one list of a model's credentials (`packages/shared/src/model.ts`): every one of these secrets comes out of every log line, progress field, error and every string in the report, wherever in a string they are and however they're written: as they are, URL-encoded (wholly or in part), JSON-escaped, hex, or base64 at any alignment (so git's basic auth header, `base64("x-access-token:" + token)`, too), along with anything shaped like a GitHub token or an `Authorization` header. The runner does it before sending; the server again before storing, broadcasting or posting anything.
- **Prompt injection.** Findings and their text come from the model and are untrusted: the web app renders them as text or sanitised Markdown, and the pull request comment escapes everything untrusted in it (finding titles, file names, OCR's warnings): every Markdown character is escaped, and mentions, `#12` and `owner/repo#12` references and bare addresses are broken up with a zero-width space, so there are no links but Triagent's own, no mentions and no HTML. A test renders the comment with a CommonMark and GFM renderer to check.
- **Exhaust resources.** A review that goes quiet is stopped as stalled, and each can have a time limit and a token budget; logs are capped at 2 MB per job; reports at 25 MB. The runner container has no inbound access, memory and process limits, and a read-only root (see `deploy/compose.example.yml`).
- **Reach the server.** The runner can only call the four runner routes, and only for jobs it holds. In the Compose example it shares a network with the server alone, never with the database.
- **The runner's own secret.** OCR runs as the runner's user, so a review that got OCR to read outside the repository (its tools are confined to it, with traversal checks, and it has no shell) could read the runner secret file and call the runner API. The runner reads the secret into memory at start-up, never passes it to OCR, and warns unless the file is readable by its owner alone (0400). Running OCR as a user of its own, who can't read it, is a later hardening step.

The separate runner process (and container) remains as defence in depth: it has no database access and nothing to steal beyond the job in hand.

## GitHub

`services/github/` connects a project to its repository in one of two modes, behind one interface (`githubFor(project) → { client, checks, repo, cloneUrl, tokenForJob() }`), with a small fetch-based REST client (no Octokit: a dozen calls don't justify the dependency).

- **The GitHub App (primary).** An instance admin creates it from Instance → GitHub App with GitHub's manifest flow (permissions: contents read, checks read, pull requests and commit statuses write; events: pull requests, pushes, branch creation and deletion, check suites, check runs, statuses and issue comments; "request user authorization during installation" on). Its id, keys, client secret and webhook secret are stored as encrypted instance secrets (`workspace_id` null), and creating or removing it needs a recent sign-in. The server signs RS256 JWTs with `node:crypto` and mints installation tokens, narrowed to the one repository. Its own, for its API calls, are cached until five minutes before they expire. Each review gets a fresh one, never cached or shared, narrowed further to `contents: read`, and revoked (`DELETE /installation/token`) when the review ends, however it ends: finished, failed, cancelled or abandoned by a lost runner. The token is sealed with the job until then, so a restarted server can still revoke it.
- **Installing into a workspace.** A workspace admin (`secrets`) starts the installation with a signed, expiring `state` bound to them and the workspace. On the way back the bare `installation_id` isn't trusted: the state must be genuine and theirs, they must still manage the workspace's secrets, and GitHub must confirm, with their own token (from the user authorization code), that their account can see that installation (`GET /user/installations`). Seeing it isn't enough, since every member of an organisation can: linking hands the workspace every repository in the installation, so for an organisation's installation they must be an owner of it (`GET /user/memberships/orgs/{org}`: `state: active`, `role: admin`; the app asks for "Organization members: read" so GitHub answers), and for a personal account's installation they must be that account (`GET /user`). An installation already linked to another workspace isn't moved. Installations are kept in `github_installations`; each project then picks a repository from its workspace's installations.
- **One app webhook** (`POST /api/v1/github/app/webhook`), checked against the app's webhook secret, routed by installation (to the workspace that linked it) and repository id (to the projects using that repository). Installation events keep the table current (removed, suspended).
- **A fine-grained token (fallback)**, stored encrypted on the project, with the project's own webhook (`/api/v1/github/webhook/{webhookId}`, its own secret). GitHub gives fine-grained tokens no way to read check runs, so a project on a token sees commit statuses only (below).
- **Automatic reviews** (`services/github/automation.ts`): with automation on, open pull requests are checked on webhook events or every `pollMinutes` (every page of them, up to the 1,000 most recently updated; beyond that, the check says so and the rest keep what's known of them). Whether to review each is decided by one pure function, `decide` in `domain/review-triggers.ts`, for the webhook and the poller alike; it answers with an action and its reason in words, or names the one thing it still needs from GitHub (checks, changed files, a diff's fingerprint, the commits since), so nothing is fetched that the decision doesn't turn on. Each answer is kept with the pull request under a key of everything it rests on (head commit, draft, labels, settings, what's been reviewed, reviews queued or running): while the key is the same, a settled answer stands and GitHub isn't asked again. Answers that wait on checks are asked about at every check; failed checks every ten minutes, or at once when an event names the commit; at most 40 pull requests are looked up per check.
  - **The first review** happens by itself when the pull request isn't a draft and (`firstReview: "checks"`, the default) every check run and commit status on its head commit has finished and passed (success, neutral or skipped), leaving out Triagent's own status. While it waits the page says for how many, and one pending "Waiting for checks to pass" status goes on the commit (one more if that ends without a review). Failed checks mean no review, naming them. A commit with no checks at all is reviewed once none have appeared for two minutes. `"ready"` ignores checks; `"manual"` never reviews by itself. A call about checks that fails is "unknown", asked again at the next check, never a pass.
  - **Checks that can't be read.** Check runs are read with a token of their own, asking for `checks: read`: an installation that hasn't accepted that permission can't be given one (and a fine-grained token can't read them at all). That is its own answer, not a pass and not a failure: commit statuses still count, and with nothing against, the pull request is reviewed when ready, saying "can't see checks, so reviewing when ready". The project's GitHub settings then say what the app needs.
  - **Later pushes** are never reviewed by themselves, nor a push while the first review is queued or running (a running review is never stopped). The page, and a last line on Triagent's comment, say how many commits since the reviewed one (the compare API; "new commits" when the branch was rebased). When a review finishes, a fingerprint of its diff is kept (a hash of file names and added and removed lines, not commit ids, hunk positions or context; none for a diff over 2 MB): a new head with the same fingerprint (a rebase, a merge from the base) takes over as the reviewed commit without a review, and the reviewed commit's Triagent status is copied to it.
  - **Skipped**, for automatic reviews only: pull requests that change only files matching the project's `skipPaths` (patterns read as .gitignore reads them, matched without regular expressions; at most 50, of 200 characters), those opened by bots with `skipBots` (GitHub's user type, or a login ending `[bot]`), and those with the label `skip-review`. Over budget has its place in the same function (`overBudget`), for cost controls to fill in.
  - **Asking** needs neither green checks nor a pull request that's ready: Review now (the API, MCP's `start_review`), a comment whose first line starts with `/review` from someone GitHub says is an owner, member or collaborator (anyone else is told who can, once per pull request), or the label `review`, which is taken off once the review is queued. Comments are read at each check (one request for the repository's new comments), each answered once. The app doesn't subscribe to `issue_comment`: GitHub only sends it to apps that can read every issue, which Triagent doesn't ask for. A repository webhook set up by hand (token connections) can send it, and then it's handled at once. A request for a commit already queued or running returns that run; one for a newer commit is queued and waits for the running one (a runner isn't handed a job while another for the same pull request runs).
  - **Fork authors and the baseline.** A review spends the workspace's model budget, so by default (`reviewPullRequestsFrom: "collaborators"`) only pull requests from a branch of the repository itself, or by its owners, organisation members and collaborators (GitHub's `author_association`), are reviewed automatically; a fork's by anyone else is listed as "Waiting for approval" until someone with `operate` clicks Review now. `"everyone"` reviews them all. Switching automation on sets a baseline: pull requests already open are listed but not reviewed until someone asks or pushes.
  - **Events.** Besides pull requests (labels included) and branches: `check_run` and `check_suite` (once completed) and `status` name a commit, and only cause a check when an open pull request is waiting on that commit; Triagent's own status coming back is ignored by its context. Events arriving together share one check. The last 50 webhook deliveries per project are kept (`github_deliveries`). Deliveries with a bad or missing signature aren't kept with them (anyone can send those, which would push the real ones out): each server process counts them, with the last reason, and the Pull requests and GitHub App pages show the count.
  - **Scheduled scans.** A nightly full scan of the default branch runs at `nightlyHourUtc`, unless the branch is still at the commit of its last full scan that finished whole: then it's skipped, and the Runs and Pull requests pages say so.
  - A failed review's commit status says only "Review failed — see Triagent for details": commit statuses are public, the runner's error isn't. With Postgres, one server process polls (an advisory lock held on a connection of its own). A pass checks up to four projects at once, and never two for the same repository at once.
- **Branch sync** lists the repository's branches: reports whose branch has moved on are marked out of date, with "N commits behind" from the compare API (at most 25 compares per sync, cached); branches on GitHub without a report are listed; and with `archiveDeletedBranches`, a branch deleted on GitHub has its report archived (never the default branch).
- **After a review** of a pull request, Triagent keeps one comment on it and sets a commit status named "Triagent": pending while queued and running, then success, failure (with `failOnCritical`, when there are critical findings) or error. The comment ends with how to ask for another review (`/review`, the `review` label, or Review now), and after it a line, replaced each time, about what has happened since: commits pushed, or a review asked for. The comment is the one Triagent wrote: remembered by id with the project's GitHub state, or else found by the hidden marker it starts with, but only among comments by Triagent's own account (the app's `<slug>[bot]`, or the token's owner from `GET /user`). Anyone can write the marker in a comment of their own; Triagent never edits those.

## The first-run tutorial

New accounts start a guided tour the first time they sign in (after any forced password change); accounts made before it existed start it once too (migration 0007 gives every user a `tutorial` of `pending`). Each person's place in it (`pending`, `in_progress` with a step, `completed` or `dismissed`) is kept on their account, so closing the browser mid-tour picks it up at the same step, and skipping it means it doesn't come back by itself. Settings → Tutorial shows it again. `TUTORIAL_AUTO_START=false` starts new accounts with it done (the end-to-end tests do, apart from their own tutorial server).

- **The routes** (`routes/tutorial.ts`): `GET` and `PATCH /api/v1/me/tutorial`, and `POST` and `DELETE /api/v1/me/tutorial/example`. They're the person's own (scope `user`) and browser-only.
- **The example project** (`services/tutorial.ts`, data in `services/tutorial-example.ts`): "Example: Acme Shop", made in the person's own personal workspace and nowhere else, once (a second request returns it), in one transaction, through the same services as real data: two reports uploaded with `reports.upload`, triage with `triage.updateIssue` by made-up people marked "(example)", and the review history of a pull request run, an upload and a partly finished scan. Its two finished runs are job records marked as examples (`result.example`), with a log saying nothing ran: no runner, GitHub or model is ever involved, and the tests check none is called. Removing it, from the tutorial or as any other project is deleted, deletes the project with its review history and its activity, so the made-up people and reviews leave the analytics too; nothing else. (Migration 0008 did the same for examples removed before that was so.)
- **The tour** (`components/tour.tsx`, `features/tutorial/`): each step goes to its page in the example project and puts a card beside the part of the page it's about, marked `data-tour="…"`, with that part lit up; when it isn't showing (a phone's folded rail), the card is a dialog in the middle of the screen. It's built on Radix Popover and Dialog and positions itself through the CSSOM, so it needs nothing the CSP refuses. Focus moves into each step, which is announced by name; Escape skips. `e2e/tutorial.spec.ts` walks every step and fails if one can't find its part of the page.

## Guided setup

Creating an organisation or a project opens its guided setup, a popup (`features/setup/`) that walks through what it needs, each step marked required, recommended or optional and ticked once the setting is in place. The steps are the same forms as in Settings, so nothing is set up twice, and a step is done when the setting is, not when someone clicked through it: the setup can be closed and picked up again without losing track.

- **Account** (after the tutorial, on the first sign-in): which finished reviews you hear about, appearance, then your workspace: set up your personal one, or create an organisation. Closing it counts as done (`tutorial.setup` on the account, `PATCH /api/v1/me/tutorial` with `setup`); accounts made before it existed are offered it once.
- **Workspace**: the review model and key (required), people (recommended, organisations only), and a first project (required), which goes on to that project's setup.
- **Project**: the repository (required), connecting GitHub (required: the app, or a token), the webhook (recommended, with a token only), automatic reviews (recommended), then starting the first review. Installing the GitHub App from here comes back into the setup (`setup: true` when starting the install; GitHub's return goes to `…/settings/github?github=…&setup=project`).
- **Finish setup**, in the top bar, shows for people who can configure the workspace while it, or the project in view, lacks something required (a model key, a project, the repository, GitHub), and opens the setup at the first thing left.

## Live updates

`GET /api/v1/w/{workspace}/events` is a Server-Sent Events stream of "something changed" notices for that workspace only. Notices about settings, members, tokens and secrets only reach people who manage them. Clients fetch details with their own permissions.

## Web app

`apps/web` is a single-page app built with Vite. The server serves the build (`http/static.ts`): only files that exist in it, fingerprinted assets cached for a year, and `index.html` for the app's own routes (`/w/{workspace}/p/{project}/issues?branch=main`). Without a build the server still serves the API.

```text
src/router.tsx       Every page and its URL; filters and the branch live in the query string
src/lib/api.ts       The one fetch layer: CSRF token on writes, a per-tab client id, typed errors (409 carries `current`)
src/lib/queries.ts   Query keys nested workspace → project → branch, and a query for each read
src/lib/live.ts      One EventSource per workspace; each notice invalidates the keys it touches
src/lib/session.ts   Who's signed in, and what their role allows, from packages/shared's permission table
src/components/reauth-dialog.tsx   "Confirm it's you" before steps that need a recent sign-in; retries the step
src/features/*       Pages: issues, tasks, overview, files, branches, compare, activity, agents, settings
src/components/*     Shared pieces: SecretField, OneTimeReveal, ConfirmAction, notes, Markdown, code diffs
src/components/field.tsx, form.tsx   Form layout: Field, FieldRow, CheckField, ChoiceField, FormSection, FormActions
```

- **Forms** follow one rule (`components/field.tsx`): the label above the control, the description below it, then the error, each tied to the control by `htmlFor` and `aria-describedby`. Fields side by side go in a `FieldRow`, a CSS grid whose fields share its lines through `subgrid`, so their controls line up however long a label or description is (`e2e/layout.spec.ts` checks it). Spacing and widths are tokens in `styles/index.css` (`gap-field`, `gap-form`, `gap-section`, `p-inset`, `max-w-narrow`, `w-control-sm` and so on), not one-off values.

- **Server state** is TanStack Query's cache; nothing polls. A live notice from another tab or agent invalidates the queries it affects. Notices carrying this tab's client id are our own changes, already applied.
- **Never clobber input.** A form being edited, or an issue with a note half-typed, holds still when the server's copy changes and shows a "changed elsewhere" banner instead (`lib/drafts.ts`). Writes send the `rev` that was on screen; a 409 shows what the other person changed.
- **Gating** uses the same permission table as the server, so the app hides what someone can't do and shows read-only settings as such. The server enforces it either way.
- **Content Security Policy.** The app runs under the server's policy (`script-src 'self'; style-src 'self'`, no `unsafe-inline`): no inline script (the theme is applied before first paint by `public/theme-init.js`), sonner's stylesheet imported statically instead of injected, Radix's scroll lock given constructed stylesheets (`lib/style-singleton.ts`) instead of `<style>` elements, fonts self-hosted, no component that renders `<style>`, and charts drawn in plain HTML and SVG (`components/charts.tsx`) rather than with a library that injects styles. Each chart has a text summary, a legend for more than one series and a table view. An end-to-end test fails on any violation.
- **Secrets** shown once (new API tokens, webhook secrets, generated passwords) live only in the state of the page that asked for them, never in the query cache, and are dropped on navigation.
